# Diesel on SQLite first, Postgres later

The asset server uses Diesel with SQLite, and is meant to move to Postgres when the platform needs
more than one instance or shares a database with the user service and scheduler. Diesel does not make
that move free (migrations are raw SQL per backend; UUIDs, timestamps and `RETURNING` differ), so
migrations stay within SQL both backends accept. Until the move, only one asset server instance may
run.

## Consequences

- **Integer ids are the one known rewrite.** `INTEGER PRIMARY KEY` columns (`movie`, `show`,
  `season`, `episode`, ...) rely on SQLite assigning the rowid on insert; Postgres accepts the
  statement but assigns nothing. Moving means rewriting those columns as identity columns
  (`GENERATED BY DEFAULT AS IDENTITY`). Keeping the SQL portable around this would cost more than
  the rewrite, so the migrations do not try.
- Schema changes SQLite cannot make in place (adding a `CHECK`) rebuild the table: create a new one,
  copy with `INSERT ... SELECT`, drop, rename, recreate the indexes. Postgres accepts the same.
